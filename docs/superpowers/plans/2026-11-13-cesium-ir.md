# Cesium IR: the engine's core IR

**Status (2026-11-13):** plan, not started. Reviewed by the owner on 2026-11-13; the answers to its questions are at the end.

**Spec:** [core-ir.md](../../design/core-ir.md) (research, spikes, and "Owner's decisions (2026-11-13)"), [investigations-2026-11-13.md](../../design/investigations-2026-11-13.md) (the toolchain research and the owner's answers), [transform-graph.md](../../design/transform-graph.md) and [styling-and-a-shared-ir.md](../../design/styling-and-a-shared-ir.md) (the transform graph and the shared IR), and the transform-graph plan's Task 9 (array parameters, bounded loops). Spike code: `packages/next/spikes/core-ir/`.

**Goal:** one core IR, **Cesium IR** (`cesium-ir`), for everything the engine takes as a function: styles, transforms and warps, materials, and user functions. Front ends lower into it. Passes run on it: float64 CPU evaluation, forward-mode autodiff, intervals, rates, literals to uniforms, and the residual and df64 forms. Back ends emit WGSL and GLSL ES 3.00 from it. Any language reaches both renderers and the CPU through it.

> **Job system (owner, 2026-11-13):** CS-58's lazily loaded naga runs as a job type on a dedicated worker group, and compiles triggered by live edits (the MaterialX example) are cancellable jobs: a newer edit cancels an older compile. See [job-system.md](../../design/job-system.md) (CS-89) and project CS-12.

**Milestones other plans depend on:**

- The WebGL 2 renderer's **CS-39** (styles and warps in GLSL ES) depends on **CS-52** (the GLSL ES 3.00 emitter), **CS-54** (routes on both emitters) and **CS-55** (styles on Cesium IR).
- The WebGL 2 renderer's **CS-40** (user hooks and post stages) depends on **CS-58** (the WGSL front end) and **CS-61** (the API surface).
- The **MaterialX live-editing example** depends on **CS-63** (the MaterialX front end, which also absorbs that plan's former task 9), **CS-55**'s uniform path and **CS-64** (noise). Its image nodes wait for **CS-65** (textures). There is no pre-IR emitter (owner, at the MaterialX review).

Milestones are named `IR-<n>` (and `IR-G<n>` for the gap list). They don't abbreviate the IR's name: "Cesium IR" stays two words, by the owner's decision 8.

## Decisions in force

From [core-ir.md](../../design/core-ir.md), "Owner's decisions (2026-11-13)":

1. **Vocabulary:** `KHR_interactivity`'s math and type nodes, names and meanings, float64 included, are normative. `cesium/` extensions are added only where it lacks an op.
2. **Serialization:** our compact versioned JSON (`cesium-ir/<major>.<minor>`, its vocabulary named, its extensions listed) is normative. A lossless writer and reader to `KHR_interactivity`'s graph JSON serves glTF interchange.
3. **GPU semantics:** the GPU side is a documented float32 approximation of float64 semantics, with df64 where a pass needs it. The CPU evaluator is the conformant one.
4. **Rust:** a Rust toolchain on development machines and CI is approved, for our own naga crate. Rust and naga never reach a production build. The crate runs in CI and in offline translation. naga loads in a browser only lazily, for the WGSL front end.
5. **WGSL is a front end, not an escape hatch.** A WGSL function is lowered through naga into Cesium IR (lazily loaded) and gets every pass. What the IR can't yet express is refused with a diagnostic. Raw WGSL that bypasses the IR isn't offered.
6. **Gap order:** textures and samplers, then matrices, then screen-space derivatives, then noise, then general bounded loops, then structs. **Amended at the MaterialX review (owner, 2026-11-13): noise (CS-64) comes first, since it needs only integer and bitwise ops and the MaterialX example's graphs all use it; it needs CS-50, CS-51 and CS-52, not CS-56. The rest keep their order after CS-56. The labels don't change.**
7. **Tables and the bounded search come first,** with the residual pass's row window, so the corridor and other table-driven warps compile to a fixed program. They also cover the transform-graph Task 9's array parameters. General loops wait.
8. **Name:** "Cesium IR" in prose; `cesium-ir` as the identifier, for the JSON format and the package. No abbreviation.

From [investigations-2026-11-13.md](../../design/investigations-2026-11-13.md) (owner's answers): styles must be evaluable on the CPU in float64; styling stays compiler-free (no Slang and no naga to style a scene); style literals become uniforms; built-in transforms are written in the IR or something that compiles to it quickly; MaterialX belongs at the edge, as an input language.

## Calls this plan makes (cheap to change; flagged for review)

- **Vectors stay vectors in the core,** as `KHR_interactivity`'s types. Passes that need scalars (the residual and df64 forms) run after a `scalarize` lowering pass, as MLIR lowers progressively. The JS transform front end keeps emitting scalars at first, so the migration is a pure move.
- **Literal identity is the slot, not the value.** Every literal a person can edit carries its place in the source. Hash-consing never merges two slots, and constant folding leaves them alone. That keeps a value edit a uniform write (spike finding 3).
- **The program's shape key** is its JSON without literal values and table data. It keys the shader module and pipeline caches.
- **A table's row count is part of the shape.** It bounds the GPU's search. To keep a pipeline per kind rather than per row count, counts are bucketed to a power of two, with padding rows that repeat the last row.
- **Every pass is an interpreter of one structure,** as JAX's are. No pass keeps a private copy of the program's form.

### CS-48: the core

**Depends on:** none.

Cesium IR as a module of its own: the program structure, the builder, the vocabulary and the float64 evaluator.

- **Structure:** typed inputs with a rate (uniform, per feature, per vertex, per fragment), typed single-assignment equations in dependency order (`op`, operands, type, and the attributes an op takes), and named outputs. Types are `KHR_interactivity`'s: `bool`, `int`, `float`, `float2` to `float4` (matrices come in CS-66).
- **Builder:** hash-consing, constant folding on `const` (never on literal slots), simplification (`x + 0`, `x · 1`, `extract(combine(…))`, `select` on a constant), dead-code removal, and the shape key.
- **Vocabulary:** the `KHR_interactivity` math and type nodes that today's IR and the style compiler use, with the spec's exact formulas. These include `mix` as `(1 - c) a + c b`, `clamp` with reversed bounds, `smoothStep`'s rising ramp, `rem` truncated, and `round` half away from zero. Each op's float64 meaning is one function, which constant folding and the evaluator share.
- **Text listing:** the jaxpr-style listing from the spike, used by tests, diffs and the inspector (CS-62).
- **Home:** `packages/next/src/ir/`, with no imports from the rest of the engine, so it can become the `cesium-ir` package without changes (question 1).

**Done when:**

- Conformance tests built from the spec's per-op tables of ±0, ±∞ and NaN cases pass for every op implemented.
- The spike's style, twist and MaterialX programs evaluate to the spike's results.
- An import-boundary test shows `src/ir/` imports nothing outside itself.
- `checkBundle` shows the core in the main chunk, with no dependency.

### CS-49: the JSON format

**Depends on:** CS-48.

The normative interchange form, `cesium-ir/1.0`.

- **Schema:** a JSON Schema in the repository. The form carries the version, the vocabulary's name, the list of extensions used, inputs, tables (from CS-56), equations and outputs.
- **Checking reader:**
  - It refuses an unknown major version, and any extension op not listed in `extensions`.
  - It checks that every operand refers to an earlier equation.
  - It re-derives every type and refuses a mismatch.
  - Its errors name the equation and the reason.
- **Versioning rules,** written down beside the schema:
  - A minor version adds ops or optional fields.
  - A major version changes a meaning.
  - Each `cesium/` extension op is a named, versioned entry in an extension registry file, as Substrait's function extensions are. An op's meaning never changes after release; a change is a new op.

**Done when:**

- Every program in the test suite round-trips through JSON to the same shape key.
- Malformed files are refused with the right message (fixtures: unknown major, unlisted extension, forward reference, type mismatch).
- The schema validates every fixture.

### CS-50: the passes

**Depends on:** CS-48.

Each pass is an interpretation of the same structure. Parity is checked against today's `src/transform` passes through an adapter (CS-53 removes the adapter).

- **Forward-mode AD:** jvp along an input's lane, Jacobian programs (three passes), Hessians (forward over forward) and parameter derivatives, as today's `ad.ts` does. A zero tangent is no node.
- **Intervals:**
  - The natural extension, lane by lane, with today's rules for sin, cos, tan, products and quotients.
  - Boolean intervals are `[0, 0]`, `[1, 1]` or `[0, 1]`.
  - **Breakpoint splitting** (`evaluateIntervalSplit`): an input's range is split wherever a branch condition or a table search changes, so no piece hulls two branches. CS-56 adds the table breakpoints.
- **Taylor bounds:** `taylorBounds.ts` moves onto Cesium IR unchanged in method.
- **Rates:** each equation's rate is the highest of its operands'. Equations at the uniform rate that aren't leaves are evaluated on the CPU in float64 and become uniforms (constant hoisting by rate).
- **Literals to uniforms:** every literal slot becomes a uniform input. The result is the program, its values by slot, and the shape key.
- **Kinks:** today's `stepIr.ts` list of ops whose derivative jumps becomes a pass that reports them per output, for the queries that need it.

**Done when:**

- Today's tests for AD, intervals, Taylor bounds, the queries and the accuracy model pass when run on Cesium IR through the adapter, with the same tolerances.
- Each pass has a test on a vector program, which today's scalar IR couldn't express.
- Breakpoint splitting gives finite bounds over a line-to-arc join (the spike's case), with no dense sample outside them.

### CS-51: the WGSL emitter

**Depends on:** CS-48 (naga validation uses naga-wasm until CS-57).

Float32 WGSL from a program, documented as an approximation of the float64 meaning.

- **Formulas:** the emitter writes `KHR_interactivity`'s formulas where WGSL's built-ins differ (`clamp`, `smoothStep`, `round`), and its own where WGSL has no op (`log10`, `cbrt`).
- **Uniforms:** one block of vec4 slots. The same layout serves GLSL's std140, so the values array is shared.
- **Function form:** non-uniform inputs become function parameters. The linker gives them their per-feature, per-vertex or per-fragment sources at the engine's existing boundaries (`src/shaders/link`).
- **Source map:** each emitted line carries its equation id, for the inspector.
- **Validation:** every module the emitter writes in the test suite is validated by naga in CI, with WebGPU's capabilities. naga-wasm serves until CS-57 replaces it. The browser suite checks the same modules with `getCompilationInfo`.

**Done when:**

- Emitted WGSL for every test program is accepted by naga (CI) and by Chrome (the browser suite).
- A GPU readback of each op over its edge cases agrees with the float64 evaluator to a stated float32 tolerance per op. The test writes the tolerances down.

### CS-52: the GLSL ES 3.00 emitter

**Depends on:** CS-51.

The WGSL emitter's twin, for the WebGL 2 renderer (CS-39 depends on this milestone).

- **Differences from WGSL:** `atan(y, x)`, `rem` through `trunc` (GLSL's `mod` is floored), the ternary for `select`, `clamp` for `saturate`, `float()` and `int()` conversions, and std140 uniform blocks.
- **Same vocabulary coverage** as CS-51. Both emitters fail the same tests when an op is missing from either.

**Done when:**

- Every program in CS-51's tests compiles and links in a WebGL 2 context in the browser suite.
- The GPU readback test passes on WebGL 2 with the same tolerances as CS-51.
- naga's GLSL ES output for one emitted WGSL module per test is compiled beside it, as a cross-check.

### CS-53: transforms move onto Cesium IR

**Depends on:** CS-48, CS-50, CS-51.

`src/transform/ir.ts` is replaced by Cesium IR. These are pure moves where possible, and every output is checked against today's.

1. **Golden fixtures first:** before anything moves, record today's outputs:
   - each built-in's parsed program listing, evaluator outputs at sample points, and Jacobians;
   - each compiled route's WGSL, per-draw and uniform layouts;
   - `test/corridorUnrollCompiled.test.ts`'s budgets.
2. **The adapter:** today's `IrProgram` to Cesium IR and back (the spike's `fromTodayIr`), with round-trip tests. Booleans become `bool` (today they are 0 and 1). `ne` becomes not-eq. `smoothstep` becomes `math/smoothStep`.
3. **Passes one at a time:**
   - `evaluate`, `ad`, `interval`, `taylorBounds`, `stepIr`, `accuracy`, `queries` and `curvature` switch to Cesium IR's passes.
   - `residual.ts` and `df64Wgsl.ts` read Cesium IR after `scalarize`.
   - Each switch is its own commit, type-checked; the full suite runs once at the end, with bisection on failure (the refactor rule).
4. **The front end:** `parse.ts` builds Cesium IR directly.
5. **Removal:** `ir.ts` and the adapter are deleted.

**Semantic changes, stated:** `clamp` with reversed bounds and `smoothstep` with reversed edges now follow `KHR_interactivity`. Tests cover both. No built-in uses either.

**Done when:**

- Every transform test passes unchanged.
- The golden fixtures match: listings up to renumbering, evaluator outputs bit for bit, compiled WGSL byte for byte or with every difference explained in the commit.
- The browser parity suites show no pixel change against the commit before CS-53 and against a base commit.
- `ir.ts` is gone.

### CS-54: routes on both emitters

**Depends on:** CS-52, CS-53.

The route compiler (`compile.ts`) writes its residual and df64 code through CS-51 and CS-52, not as WGSL strings. The WebGL 2 renderer's warps need this (CS-39 depends on it).

- **Residual pass output:** the pass emits Cesium IR equations over (centre value, change) pairs, with the residual helpers as library functions. The emitters write either language.
- **df64 centre pass:** it stays a WebGPU compute pass. On WebGL 2 the centre constants come from the CPU in float64. The renderer's support report says so.
- **Normals:** the "exact", "linear" and "auto" modes are carried over unchanged.

**Done when:**

- Compiled routes for every built-in agree between the two emitters on the GPU readback test.
- The WebGPU output matches CS-53's golden fixtures.
- On WebGL 2, the corridor baseline holds: map within 10⁻⁸ m of the CPU map, Jacobian within 10⁻⁹, and float32 change from the draw centre under 0.1 mm.

### CS-55: styles move onto Cesium IR

**Depends on:** CS-50, CS-51, CS-52.

`styleExpression.ts` lowers to Cesium IR instead of writing WGSL strings. `FeatureStyle` and `VectorStyle` use the emitted code.

- **Literals to uniforms** ([investigations-2026-11-13.md](../../design/investigations-2026-11-13.md), decision 8): a style's literals are uniforms. A value edit is a buffer write. Shapes share a pipeline through the shape key.
- **Style changes:** `Tileset3D` gets a way to change its style (today it's a constructor option only).
- **Strings:** string ids (`stringIds.ts`) stay as they are. A string literal's id is a uniform literal.
- **Colours:** the colour rule in `cssNotation` (linear output) is unchanged.
- **CPU evaluation** ([investigations-2026-11-13.md](../../design/investigations-2026-11-13.md), decision 1): `FeatureStyle.evaluate(feature)` returns `show`, `color` and the other fields in float64, for picks, legends and queries. String properties compare by id on the CPU as on the GPU.
- **Interval culling of tiles:** a style's `show` over a tile's property ranges (from 3D Tiles statistics or metadata), through CS-50's intervals. A tile whose `show` is false over its whole range is culled before it's drawn.
- **Compiler-free styling, guarded:** `checkBundle` and `test/styleNoSlang.test.ts` extend to naga. Styling a scene loads neither Slang nor naga.

**Done when:**

- `test/styleParity.test.ts` (1.x as oracle), `test/style.test.ts` and `test/vectorStyle.test.ts` pass unchanged.
- `FeatureStyle.evaluate` agrees exactly with 1.x's CPU `Cesium3DTileStyle` on the parity styles (the spike's result).
- The `tileset` parity suite with styles shows FLIP at the unstyled baseline.
- A value edit makes no new module or pipeline (a fake-GPU count test, as `test/styleCost.test.ts`).
- The bundle guard passes.

### CS-56: tables and the bounded search (the first extensions)

**Depends on:** CS-53, CS-54.

The owner's decision 7. A table-driven warp becomes a fixed program over data.

- **Tables:**
  - Typed constant tables of named float columns. Their data is an input, so an edit is a buffer write.
  - The row count is part of the shape, bucketed.
  - GPU storage is a read-only storage array (WGSL), or a std140 uniform block of vec4s, or a float texture when the data is larger than a uniform block (WebGL 2).
  - On the CPU, a typed array.
- **`cesium/search`:** the last row whose column is at most the key, a binary search bounded by `ceil(log2(rows)) + 1` steps, a constant (the GPU safety rule). **`cesium/tableGet`:** a row's column.
- **The passes:**
  - _AD:_ a search and a table read are piecewise constant, so their tangent is zero.
  - _Intervals:_ a search maps a key range to a row range, and a table read takes the hull over those rows. Breakpoint splitting at the table's values gives each piece one row.
  - _Rates and hoisting:_ tables are uniform-rate data.
  - _Residual — the row window:_
    - A draw stores its centre's row per table and the rows either side, chosen to cover the draw's radius. For each window row it stores the centre values the rules read, the crossing term `v_i(c) - v_ic(c)`, and the window's breakpoints relative to the centre.
    - A vertex picks its row by comparing its float32 offset with the breakpoints; there is no search per vertex.
    - Within a row, table values are constants.
  - _df64:_ the per-draw search runs on (hi, lo) copies of the table.
- **The corridor:** `corridorUnroll` becomes one program over a plan table, with a profile table for elevation (as the spike's input 5). The polyline's corners get the arc fillets the transform-graph Task 9 asks for, as table rows.
- **Task 9's array parameters:** lattice control points and polygon vertices (flatten) become tables, so one pipeline serves every lattice or polygon of a kind.

**Done when:**

- The 39-line road compiles to the same program as a 3-element alignment: same equations and same shader, with only table data differing.
- The road's per-draw floats are at most what a window covering the largest draw needs. The test writes the window rule down.
- The corridor baseline holds on the compiled route: map within 10⁻⁸ m, Jacobian within 10⁻⁹, float32 change under 0.1 mm, offsets to ±1.5 km.
- Lattices and flattens of one kind share a pipeline (a fake-GPU count test).
- The plan-and-profile scene's first warped draw is no longer held by the corridor's compile. The example's refinement chip shows no "compiling" entry for it.

### CS-57: our naga crate

**Depends on:** none (can start at any point).

The owner's decision 4: a Rust crate over naga with exactly the API the engine needs, built in CI.

- **API (the spike's `naga-crate/`):**
  - parse and validate WGSL with WebGPU's capabilities (not every capability, as naga-wasm does);
  - write GLSL ES 3.00 for an entry point;
  - write SPIR-V with debug names;
  - optionally, export naga's IR as JSON.
- **Build:**
  - pinned naga and wasm-bindgen versions;
  - `wasm32-unknown-unknown`, then wasm-bindgen, then `wasm-opt -Oz`;
  - a CI job builds it and records the wasm's size in `bench/results`.
- **CI validation:** the crate replaces naga-wasm for validating every generated WGSL module: the engine's `src/shaders/generated`, and CS-51's emitted modules. Where naga and Tint disagree, the case is recorded ([investigations-2026-11-13.md](../../design/investigations-2026-11-13.md) spike b).
- **Offline translation:** the WebGL 2 renderer's whole-module shaders, written in WGSL, are translated to GLSL ES 3.00 at build time by the crate.

**Done when:**

- CI builds the crate from a clean checkout.
- The validation job runs on every pull request.
- The size is recorded.
- naga-wasm is removed from the spike folder's dependencies.
- No production build contains the crate's wasm, except the lazy chunk CS-58 adds; `checkBundle` guards this.

### CS-58: the WGSL front end

**Depends on:** CS-48, CS-57.

The owner's decision 5. A WGSL function is lowered into Cesium IR, lazily loaded. The WebGL 2 renderer's user hooks need it (CS-40 depends on it).

- **Path:** WGSL → naga (CS-57's crate, as a lazy chunk, as runtime Slang is) → SPIR-V → Cesium IR. SPIR-V is the stable bridge; naga's own IR changes every quarterly major ([core-ir.md](../../design/core-ir.md)).
- **The subset:** straight-line functions of the vocabulary, plus whatever the gap list has added. Each SPIR-V construct maps to an op or is refused.
- **Diagnostics:**
  - What the IR can't express is refused with the WGSL source span, from SPIR-V's line information.
  - The message names the construct and the gap milestone that would add it. Examples: a texture sample before CS-65, a loop before CS-68, a struct before CS-69.
  - naga's own parse and validation errors pass through, formatted.
- **Literals:** WGSL literals are float32, so the front end records each as a literal slot with its float32 value. The CPU evaluator then sees the same constants as the GPU.
- **Slang:** offline Slang reaches Cesium IR through its WGSL output and this front end (question 2).

**Done when:**

- The spike's WGSL function lowers and evaluates exactly against its float64 form, and its gradient matches central differences.
- Every refused construct in a fixture list gives its diagnostic with the right span.
- `checkBundle` shows naga only in a lazy chunk.
- A page that never uses a WGSL function never fetches it.

### CS-59: the KHR graph JSON writer and reader

**Depends on:** CS-49, and CS-56 for tables.

The owner's decision 2: lossless interchange with glTF's `KHR_interactivity`.

- **Writer:**
  - math and type nodes as declarations and nodes, with operand references to lower node indices (the IR's own order);
  - inputs as graph variables;
  - rates, literal slots, tables and `cesium/` ops in a Cesium vendor extension on the graph (question 3);
  - the IR's version in the extension, since `KHR_interactivity` has none.
- **Reader:** accepts the pure data subgraph (math and type nodes, variables). It refuses flow, pointer, animation and event nodes with a diagnostic. It restores rates, slots and tables from the extension.
- **Sockets:** each op's socket names are checked against the spec's text. A table of them lives beside the vocabulary.

**Done when:**

- Every test program round-trips Cesium IR → KHR JSON → Cesium IR to the same shape key and the same literal values.
- The written files validate against `KHR_interactivity`'s JSON schemas.
- A file using a flow node is refused with its node index named.

### CS-61: the API surface

**Depends on:** CS-49, CS-55, CS-56, CS-58.

What the public API takes, so a new language never touches the core ([investigations-2026-11-13.md](../../design/investigations-2026-11-13.md): "the IR is the contract").

- **A program is the normative input** wherever the engine takes a function:
  - a style's fields (`FeatureStyle`, `VectorStyle`);
  - a smooth edge's function (`smooth`, `fromFunction`);
  - a custom shader's hooks (the material's inputs, the vertex displacement);
  - post stages.
- **Languages are entry points of their own,** loaded on demand:
  - the core (types, builder, evaluator, JSON, the KHR writer and reader);
  - the 1.x style language (main chunk: styling must stay cheap);
  - restricted JS;
  - MaterialX;
  - WGSL functions (lazy, CS-58).
  Each takes source text and returns a program, or diagnostics.
- **Convenience forms stay:** `FeatureStyle({ color: "${Height} > 50 ? …" })` still takes a 1.x string. It lowers through the style entry point, as today's constructor parses.
- **`CustomShader`:**
  - Its raw `wgsl`, `vertex` and `fragment` strings are replaced by hooks that take programs or WGSL functions (lowered through CS-58).
  - `CustomShader.fromSlang` either stays as Slang → WGSL → Cesium IR, both lazy, or goes (question 2).
  - Existing examples move to the new form.
- **Support reports:** a renderer reports which `cesium/` extensions and gap features it supports (`view.support`). A program using an unsupported one warns once and falls back as the engine profiles plan says.
- **Entry points and boundaries:** `@cesium/next/ir` (or the `cesium-ir` package, question 1); `api/surface.txt` updated; `test/importBoundary.test.ts` rules that the core imports no front end and no front end imports another.

**Done when:**

- `npm run surface` shows the new entry points.
- The import-boundary test enforces the rules.
- Every example uses the public forms.
- The handbook's shading and architecture tabs describe the contract, with their "checked" dates and statuses updated.

### CS-62: the inspector and debugging

**Depends on:** CS-51, CS-55 (CS-58's diagnostics when it lands).

How a program is shown to the people who write it and the people who debug it. It extends `widgets/inspector.ts`.

- **Listing:** the jaxpr-style text, with each equation's rate and, for a picked feature or vertex, its float64 value.
- **Graph view:**
  - nodes coloured by rate;
  - literal slots with live values, editable in place (a uniform write);
  - tables as a data grid.
- **Emitted code:** WGSL and GLSL side by side, each line linked to its equation through CS-51's source map.
- **Why this value:** for a picked feature, the CPU evaluation traced through the equations ("`show` is false because `v8: Height > 120` is false").
- **Costs:** per program, its shape key, whether the last edit was a uniform write or a new pipeline, and the module and pipeline times.
- **Diagnostics:** front-end refusals (CS-58), reader errors (CS-49, CS-59) and support-report fallbacks (CS-61), with their spans.

**Done when:**

- The inspector shows each of these for a styled tileset, a warped route and a MaterialX material.
- Its page passes the UI checklist in `AGENTS.md` (both themes, 380 px, keyboard, reduced motion, clean console).

### CS-63: the MaterialX front end

**Depends on:** CS-50, CS-51, CS-55.

The edge input language for the live-editing example.

- **Reading:** the MaterialX plan's document layer (`packages/next/materialx/`): our own small XML reader, which runs in workers and Node, and a generated table of node definitions from MaterialX 1.39.5. JsMaterialXCore loads only to upgrade a document older than 1.39 (question 4, amended at the MaterialX review).
- **Owns the lowering** that the MaterialX plan's task 9 had: there is no pre-IR emitter to retire.
- **Mapping:** stdlib pattern nodes map to the vocabulary through a table:
  - `absval` to `math/abs`, `subtract` to `math/sub`, `ln` to `math/log`, `magnitude` to `math/length`, `dotproduct` to `math/dot`;
  - `modulo` is floored;
  - `mix (fg, bg, mix)` becomes `math/mix(bg, fg, mix)`;
  - `geompropvalue` becomes a per-feature input;
  - `texcoord` and `position` become per-vertex inputs.
- **Slots:** each node input's value is a literal slot `node.input`, so slider edits are uniform writes.
- **Refusals:** an unsupported node is refused with a diagnostic naming it. Image nodes wait for CS-65. Noise is CS-64, which comes first among the gaps.

**Done when:**

- The spike's graph lowers and evaluates to the spike's results.
- Value, category and wiring edits behave as the spike measured: a value edit is a uniform write; category and wiring edits are new shapes.
- A fixture of every stdlib node in the mapping table evaluates against MaterialX's own definitions on sample inputs.

### The gap list (owner's order)

Each gap milestone adds its construct to the vocabulary or extensions, the evaluator, AD, intervals, both emitters, the residual and df64 forms where transforms use it, the JSON and KHR forms, and the WGSL front end's mapping. It also removes the construct from CS-58's refusal list. Each depends on the one before it and on CS-56, except CS-64 (noise), which comes first and needs only CS-50, CS-51 and CS-52 (amended at the MaterialX review, owner, 2026-11-13). CS-65 then follows CS-64 and CS-56.

- **CS-65: textures and samplers.**
  - Texture and sampler inputs at the uniform rate, and a sample op.
  - CPU evaluation through a CPU sampler matching the GPU's filtering within a stated tolerance.
  - AD through bilinear filtering (piecewise linear in the coordinates).
  - Intervals from a min/max mip pyramid over the footprint.
  - Serves imagery and MaterialX image nodes.
- **CS-66: matrices.** `KHR_interactivity`'s `float2x2` to `float4x4` and its matrix ops (`matMul`, `transform`, `transpose`, `determinant`, `inverse`), with residual and df64 rules.
- **CS-67: screen-space derivatives.**
  - Derivative ops at the fragment rate only, enforced by the rates pass.
  - CPU evaluation as the forward-mode derivative along the pixel's footprint.
  - Procedural patterns use them for antialiasing.
- **CS-64: noise.** MaterialX's noise functions (`noise2d`, `noise3d`, `fractal3d`, `cellnoise`, `worleynoise`), written as Cesium IR library functions on the vocabulary's integer and bitwise ops, so every pass applies. They match MaterialX's reference outputs within a stated tolerance.
- **CS-68: general bounded loops.**
  - A loop with a constant maximum iteration count and an early exit, unrolled when short.
  - AD of fixed-point solves by the implicit-function theorem, not through the iterations (transform-graph Task 9).
  - Intervals bound the converged map.
  - This lets inverses of bump, lattice and flatten compile.
- **CS-69: structs.** Record types for grouped inputs and outputs (material inputs), removed by `scalarize` before the emitters and the residual pass.

## Testing and process

- **Tasks:** milestones are carried out task by task with a fresh reviewer per task (`AGENTS.md`). Design-heavy milestones (CS-48, CS-54, CS-56, CS-61) get the most capable model for design and review.
- **Tiered tests:** focused tests while iterating, and the full `npm test` before each commit. The browser parity suites run for CS-53, CS-54, CS-55 and CS-56, against the previous commit and a base commit.
- **Pure moves (CS-53):** type-check per commit; run the full suite and the gates once at the end, with bisection on failure.
- **Bundle and boundary guards:** `checkBundle` and the import-boundary test change with the milestones that need them (CS-48, CS-55, CS-57, CS-58, CS-61).
- **The handbook:** each milestone that changes what a tab describes updates it in the same change (shading, architecture, differences).
- **Spike code:** `spikes/core-ir/` stays as the record until CS-56 lands, then it is removed, with any still-useful test moved into `test/`.
