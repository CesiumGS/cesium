# Brainstorm: a styling language of our own, on the IR (owner, 2026-11-12)

**What this holds:** A styling language of our own on the IR, with its open questions (owner, 2026-11-12). Moved from the overall plan (`CESIUM2_WEBGPU_PLAN.md`) on 2026-11-13, with its content and dates unchanged.

**The owner's direction:**

- **One general-purpose styling language** for vectors, geometry and 3D content, specified apart from 3D Tiles. 3D Tiles content is one thing it styles, and 3D Tiles 1.x styles can be one of its inputs, but it isn't a 3D Tiles feature.
- **The language itself is the open question.** The ideas from the owner's vector style lab carry over, above all its pipeline and what the runtime must supply. Its spec text, syntax and code don't come into this repository.
- **It's built as a layer on the IR** ([transform-graph.md](transform-graph.md), [styling-and-a-shared-ir.md](styling-and-a-shared-ir.md)), next to the shading toolchain.
- **The main question:** how values the runtime provides (the view, time, feature state, geometry measures, generated items) are exposed in the language and generated by this engine.

## 1. Ideas to carry over (from the lab, in our words)

- **A pipeline per layer:** select features, transform their geometry through a chain of operators, then draw one mark.
  - _Operators_ derive geometry (outlines, shared boundaries, anchor points), place items (points along a line, grids and scatters in a polygon, parallel offsets), generate lines (hatches, contours, flow lines) or aggregate (clusters, density).
  - _Marks_ are a fill, a stroke, a symbol, text or a solid. They share one paint model: colour, patterns, dashes, an outline, casing or halo, and a material.
- **Every field can be data-driven.** Each field is evaluated at the rate its inputs vary: once per style, per feature, per item an operator produced, or per vertex.
- **Lengths carry units:** screen pixels, paper millimetres at a reference scale, and ground metres. They're checked when a style compiles.
- **What the data must supply follows from the style.** A style's inputs determine a data-requirements manifest, which a tiler or data service can read.
- **Placement and collision are one pass per frame** across all layers and all composed content. Occluded marks can show as ghosts.
- **Scales and legends come from the same definitions.** Drawing order is in explicit bands, and styles compose (a base and its overrides).
- **A small core plus named extensions,** with conformance levels from 2D, through draped on terrain and tiles, to free in 3D.

## 2. Overlap with shading languages: the same IR, different rates

- **Styles and shaders are the same kind of program.** A style's fields and a shader's code are both pure expression graphs over typed inputs, and they differ in the rate each value varies at: per style, frame, view, feature, item, vertex or fragment.
- **Prior art for rates:**
  - "A real-time procedural shading system for programmable graphics hardware" (Proudfoot, Mark, Tzvetkov, Hanrahan, SIGGRAPH 2001) partitioned shaders by computation frequency;
  - Spark (Foley and Hanrahan, SIGGRAPH 2011) made rates types;
  - RenderMan has uniform against varying values.
- **One IR with rate inference** splits a style into:
  - a CPU part;
  - a per-feature or per-item compute pass that writes a style table;
  - vertex and fragment parts.
- **Styling meets shading at material inputs.** A style's paint feeds the engine's material (colour, opacity, emissive, metallic and roughness). Anything beyond that is a shading function through the same IR, as MaterialX's pattern graphs meet its surface shader.
- **Geometry-changing fields depend on the kind of change:**
  - fields that move geometry (offsets, extrusion heights, a profile's exaggeration) are smooth nodes ([transform-graph.md](transform-graph.md)), so true and drawn picks come for free;
  - operators that change topology (items along a line, hatches, contours) are compute passes emitting into indirect draws, as the b-rep dicing does.

## 3. The runtime contract: how provided values reach the language, and how this engine makes them

**In the compiler, every value the runtime supplies is a declared input** with three parts:

1. **A name** in the language, abstract, such as `view.metresPerPixel` or `feature.id`.
2. **A type,** with a unit where it has one.
3. **A rate.**

The engine keeps a registry of _providers_, one per input, for each kind of content. 3D Tiles content is one provider set (property tables, feature IDs). Vector sources, point sources, b-reps and point clouds are others. This is what keeps the language apart from 3D Tiles.

**How it compiles:**

- The IR's rate inference puts each field at the slowest stage its inputs allow.
- The compiler generates the bindings and the access code for each stage.
- The style's manifest is the set of inputs it uses.
- A style that reads an input no provider supplies for that content is refused, naming the input and the content.

| Input                                                                                                              | Rate                                  | Where this engine has it today                                                                     | How it would be bound                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Feature properties                                                                                                 | Feature                               | 3D Tiles property tables (the 1.x style binding, `FeatureStyle`); typed columns on a `PointSource` | Columnar storage indexed by the feature's index, typed in the IR                                                                          |

A provider maps it from the content's own ID semantics. **Gap:** not stable across tiles today |

**What the language gives back:**

- each mark's channels, into the vertex and fragment stages or the style table;
- label requests, for the per-frame collision pass, which is on the CPU in the lab and a GPU candidate here;
- legend entries, from a CPU evaluation of the scales;
- pick payloads.

**Status in this engine:** only the point path exists (`src/vector/VectorStyle.ts`, ported earlier). It compiles a subset of the lab's language per point to WGSL, with properties, parameters, view distance and time as inputs. Everything else in the table marked as a gap is unbuilt.

## 5. The language: open

The owner's question. Options:

- **(a) A declarative document with expressions,** as most style languages do (1.x styles, MapLibre).
- **(b) Restricted JS/TS:** functions per field and a builder for layers, parsed to the IR as the transform graph's functions are ([transform-graph.md](transform-graph.md), [styling-and-a-shared-ir.md](styling-and-a-shared-ir.md)).
- **(c) Both, lowered to one JSON interchange of the IR,** which other runtimes (cesium-native) implement. 3D Tiles 1.x styles would be a third front end.

Whatever the surface, the pipeline (§1) and the runtime contract ([architecture.md](architecture.md)) are the parts to settle first, because both front ends lower to them.

**Other open questions:**

1. **The spec:** where does the language live, as a standalone spec referenced by 3D Tiles and by applications? Which runtime classes does it define (2D, draped, free 3D)?
2. **Element-wise overrides** ([infrastructure-and-geoscience-capabilities.md](infrastructure-and-geoscience-capabilities.md)): are they feature state read by expressions, or an override table applied after the style?
3. **Labels:** can collision move to a GPU pass, or does text keep a CPU-rate stage?
4. **Porting order:** the engine's next mark kinds are lines and polygons (on the vector design's shared curve, coverage and stroke kernels, [cad-display-extensions.md](cad-display-extensions.md), [breps-and-geometry-queries.md](breps-and-geometry-queries.md)), then marks over existing 3D content (mesh features, b-rep faces and edges, point clouds, [lidar-example.md](lidar-example.md)). Should they be built on the IR from the start?

**Spikes, after the IR work of [styling-and-a-shared-ir.md](styling-and-a-shared-ir.md):**

- **(a) The provider registry and rate inference:** compile one point layer and one line layer, with every input declared, and generate their bindings.
- **(b) Feature state:** a per-world state table by stable ID, read by a style (hover and selection), across tiles.
- **(c) One style over points, lines and b-rep faces.**
- **(d) Two kinds of operator:** a moving operator as a smooth node (parallel offsets) and a generating one as a compute pass (items along a line).
