## Layout

The final layout, after CS-611 has taken 1.x out and CS-835 has moved 2.0:

```text
/                                 the workspace root: private, named cesium-workspace, never published
  package.json                    workspaces: packages/*, apps/*, tools/*; the repository's scripts
  package-lock.json               committed, the one lockfile for every workspace ("Installs and the lockfile")
  tsconfig.json                   the references to every package and to the harness
  tsconfig.base.json              compiler options every package shares (today's packages/next/tsconfig.json)
  vite.config.ts                  the dev server and Dyno's routes (today's packages/next/vite.config.ts)
  vitest.config.ts                the one suite (split out of vite.config.ts)
  packages/
    cesium/                       the umbrella, development name @cesium/next until CS-616's names are final
    core/  time/  frames/  crs/  measure/  ui/
    crs-proj/  ion/  itwin/                                   (as their seams land: the package map)
    source-3d-tiles/  loader-gltf/  loader-draco/  loader-basis/
    imagery-url-template/  imagery-bing/  imagery-quantized-mesh/
    data-node/
  apps/
    sandcastle/                   private, until its own repository
  tools/
    dyno/                         @cesium/dyno, private
  test/                           one suite, as today
  parity/  bench/  lab/  handbook/  examples/  demo/  spikes/  standalone/
  scripts/                        build, release, shaders, surface, checks
  api/surface.txt
  work/                           the tracker (today's packages/next/work)
  docs/                           design notes and decisions (today's docs/ and packages/next/docs/)
  .github/  .husky/  .human-in-the-lead/
  AGENTS.md                       one file: today's root contract and packages/next/AGENTS.md together
  LICENSE.md  README.md  CHANGES.md
```

- **Packages hold only what publishes.** `packages/*` is the set the release script versions and packs. Private workspaces sit in `apps/` and `tools/`, so a glob over `packages/` never has to skip one. Today's root lists 1.x's private Sandcastle among published packages; this keeps them apart.
- **Each package** is laid out as the package map says (folder name is the package name without the scope; today's folder names inside `src/`), plus what publishing needs: `package.json` with `files: ["dist", "LICENSE.md", "README.md"]`, a `tsconfig.json` with `composite: true` and its sibling references, a README and the license. Its build output goes to `dist/`, which git ignores.
- **The harness stays at the root, not in a package.** Tests, parity pages, Dyno's suites, the handbook and the examples exercise the whole engine and import packages by name. That matches the package map, which keeps one suite and puts the tools beside the umbrella.
- **Where the rest lives.** Sandcastle in `apps/sandcastle`. Dyno's command line in `tools/dyno`, its suites, pages and results code in `bench/`, its results store outside the repository as today (`~/.cesium-bench`). The handbook in `handbook/`, built into one HTML file as today. Examples in `examples/`, with their own shaders' `generated/` beside them. Shaders' generated output in `packages/core/src/shaders/generated/` and `packages/core/src/render/generated/`, checked in. The tracker in `work/`, with hitld's settings in `.human-in-the-lead/`. Design notes, decisions, plans and history in `docs/`, with `packages/next/docs/`'s three 1.x specs joining `docs/design/`; the overall plan, `CESIUM2_WEBGPU_PLAN.md`, stays at the root as their index.
- **The workspace root is private and has a name of its own.** The root's `package.json` is named `cesium` today (1.x). Once 1.x leaves, the root is renamed `cesium-workspace`, marked private, so the umbrella in `packages/cesium` can take `cesium` when CS-616 is final. The package map's "one constraint on publishing `cesium`" goes away with it.
- **Node.** `engines` stays `>=24`, as today. CI tests on Node 24 and the current release.

**What it departs from.** Most TypeScript monorepos written up in 2026 add a task runner, Turborepo or Nx, on top of the workspaces, for caching and affected-only runs (sources: Nx's comparison, the DEV write-ups). This design doesn't, for alpha.1. The per-package JavaScript builds are independent of each other (siblings are external, below), `tsc --build` orders the declarations, and the slow parts of this repository's checks (the GPU suites, `test:data`) aren't cacheable task outputs anyway. A runner is a later call if CI time says so. pnpm's stricter installs would catch undeclared dependencies; the import-boundary test catches them instead (below), and npm stays, because hitld's worktree setup, Dyno's release store (`npm pack`) and every script assume it.

## Installs and the lockfile

**Today, no install is reproducible.** The root `.npmrc` says `package-lock=false` and `.gitignore` lists `package-lock.json`, 1.x's long-standing choice. Every `npm install`, in every worktree and every CI job, resolves the ranges in the `package.json` files anew. On 2026-11-21 a fresh worktree resolved `@playwright/test` (`^1.62.1`) to 1.65.1 while the main checkout has 1.64.1, so two checkouts of one commit ran different tools. Most of 2.0's own runtime dependencies are exact pins, but its dev dependencies (`vitest ^5.0.5`, `typescript ^6.0.2`, `ktx-parse ^2.0.0`, `meshoptimizer ^1.2.0`) and every transitive dependency float.

**The design: the 2.0 branch commits one lockfile** and installs from it everywhere.

- **One `package-lock.json` at the root,** for every workspace, committed. CS-611 removes `package-lock=false` from `.npmrc` and `package-lock.json` from `.gitignore`, on the 2.0 branch only; `main` keeps 1.x's practice. The first lockfile is written once, in CS-611, seeded from the versions the main checkout has installed (npm records them in its `node_modules/.package-lock.json` even with `package-lock=false`), then reconciled with `npm install --package-lock-only`, and its diff against those versions is checked to move nothing.
- **`npm ci` everywhere it installs:** hitld's worktree setup (`npm ci --ignore-scripts --no-audit --no-fund --prefer-offline`), every CI job, the release workflow and Dyno's snapshot worktrees. `npm ci` fails when `package.json` and the lockfile disagree, so a forgotten lockfile change fails the fast tier instead of resolving silently. `npm install` stays for the person changing a dependency.
- **Dependency updates come as reviewed changes.** Dependabot's `npm` updates, grouped (development tools weekly in one change, runtime dependencies one at a time), each through the merge queue like any change. It ignores `cesium-1x` (the oracle moves only on purpose) and anything exact-pinned for a reason, such as `naga-wasm` and the Slang toolchain. This is a new service on the repository, so it is part of question 8.
- **Users still get ranges.** npm never publishes `package-lock.json`, and the packages don't ship `npm-shrinkwrap.json`, which npm advises libraries against, because it would take the choice of transitive versions away from applications. So the lockfile pins this repository's development, CI and release, not what an application installs.
- **What users resolve is tested too.** A nightly CI job installs with the lockfile set aside (`npm install --no-package-lock` in a clean checkout) and runs the fast and full tiers, so a new release of a dependency that breaks the packages shows up before a user finds it. OpenSSF's guidance for library authors argues for this half; the committed lockfile is the other half.
- **The toolchain is pinned beside it.** `engines` keeps `node >=24`, and the CI jobs and worktree setup use one npm major, the one the lockfile was written with. Whether `package.json`'s `devEngines` field can enforce that for people too is CS-612's to check in npm's documentation; this note didn't verify it.

What it replaces: 1.x's resolve-on-every-install, and today's worktree setup, `npm install --ignore-scripts --prefer-offline`, which picks whatever the cache and the registry hold that day.

## Build

### What exists today

2.0 already has no gulp. Its dev server, its library build (`vite.lib.config.ts`: six entries into `dist-lib/`, shaders inlined, the worker and the Draco and Basis WebAssembly as assets) and its declarations (`tsc -p tsconfig.lib.json`, then `tsconfig.lib.widgets.json` against those declarations through `paths`) are Vite and `tsc`. gulp runs only for 1.x: `prepare`, `build`, `buildTs`, `release`, `makeZip`, the Karma tests and the website deploys. The root's `prepare` script still runs `gulp prepare`, and hitld's worktree setup still runs `npx gulp prepare` and three gulp builds of 1.x's packages. That is why a new 2.0 worktree can fail to install on a 1.x tool.

### The new build

One command builds every package: `npm run build`, which runs `scripts/build.mjs`.

1. **Declarations:** `tsc --build` over the root `tsconfig.json`, whose references name every package. Each package emits per-file `.d.ts` into its `dist/types/`, with `rewriteRelativeImportExtensions` as today. Project references resolve siblings through the workspace links, so the widgets' `paths` workaround in `tsconfig.lib.widgets.json` goes away. `stripInternal` stays on for every entry but core's `./internal`, whose names siblings' declarations import (CS-883); that subpath is outside the stable API by its name and by the surface check, not by stripping.
2. **JavaScript:** one Vite library build per package, from one shared function (`scripts/build/library.mjs`, given the package's folder). It reads the entries from the package's `exports`, builds ESM only, target `es2023` as today, and:
   - **treats every dependency and peer dependency as external,** siblings included. Each package's code exists once in an application, so `instanceof Emitter` holds across packages, and the per-package builds don't depend on each other's output;
   - **keeps modules as files** (`preserveModules`), so an application's bundler tree-shakes by file and the package's `sideEffects` decide what it pays for, as the bundle check expects;
   - **inlines shaders** (the 43 `?raw` imports of generated WGSL today) and emits workers and WebAssembly as assets found through `import.meta.url`, as today's library build does. Plain `tsc` can't build this, which is why the JavaScript goes through Vite;
   - **runs the same guards as today:** the sky-pack guard and the Basis glue (`basisTranscoderEsm.ts`) move to `scripts/build/` and apply in every package's build.
3. **The browser build (CS-363):** the umbrella also builds today's `dist-lib` shape into `packages/cesium/dist/browser/`, every package bundled in, for pages with no build step. npm's CDNs serve it from the published `cesium` package. It replaces 1.x's `Build/Cesium` and the release zip.
4. **Checks on the packed result:** `npm pack` per package, then `scripts/checkDeclarations.mjs` (today's, run over every package), and `publint` and `@arethetypeswrong/cli` on each tarball if the owner agrees to them (question 6). Without them, `checkDeclarations.mjs` grows the export checks itself.

**The export condition (a call, reversible).** Today's exports point at `./src/index.ts`, which is right for development and wrong for a published package. Each package's `exports` gets a private condition first, then the published files:

```json
"exports": {
  ".": {
    "@cesium/source": "./src/index.ts",
    "types": "./dist/types/index.d.ts",
    "default": "./dist/index.js"
  }
}
```

`tsconfig.base.json` sets `customConditions: ["@cesium/source"]`, and the Vite and Vitest configs add it to `resolve.conditions`, so development, the tests and Dyno run from source with no build, as they do today. The release script removes the condition from the published `package.json`, so no consumer can resolve a file that isn't in the tarball. A scoped name, not `source`, because other tools already use `source`. npm can't do this with `publishConfig`, which doesn't override `exports`; pnpm can, but this repository stays on npm.

**Type rollups are deferred.** One `.d.ts` per entry would be tidier, and it's what API Extractor's rollup or `rolldown-plugin-dts` give. But API Extractor's own value here, release-tag trimming and `ae-incompatible-release-tags`, is what CS-681 already rebuilds in `scripts/surfaceMap.mjs`, and `rolldown-plugin-dts` is pre-1.0 and fast only with `isolatedDeclarations`, which today's code doesn't satisfy. Per-file declarations resolve correctly through `exports`, and the packed-tarball checks prove it. Revisit after the API review (CS-102), when the surface is stable. Turning on `isolatedDeclarations` is a separate, later item: it needs explicit types on every export, which is engine code.

### Shaders

Nothing changes in how shaders build. Slang sources stay in `packages/core/src/**/*.slang` (and examples' own); `npm run shaders` (`scripts/slangBuild.mjs`) writes `packages/core/src/shaders/generated/` and `packages/core/src/render/generated/layouts.ts`; the generated files stay checked in, so `npm run build`, the tests and CI's ordinary jobs need no compiler. `SLANGC` still names the compiler, and `npm run setup` still fetches the pinned one. What changes:

- `slangBuild.mjs` moves to the root `scripts/` and takes a list of package source roots instead of one `src/`. Core is the only one at alpha.1. A later adapter with shaders of its own (a Gaussian-splat render feature, say) adds its root, and core's shader modules stay on the include path for it.
- CI's `shaders` job fetches the pinned `slangc` release, checks it against its recorded hash, caches it, and runs `npm run shaders:check`. Today nothing runs that check outside the merge queue's full suite.

### The bundle check, the surface and the handbook

- **The bundle check** (`scripts/checkBundle.mjs`) stays a Vite build of small application pages, run in the full tier. It builds them against the packages' `dist/` output, not their source, so it checks what users get; it gains the time-only and frames-only pages (below, under "Tests and gates").
- **The surface** (`npm run surface`, `scripts/surfaceMap.mjs`) reads every package's `exports` instead of one package's, writes `api/surface.txt` per package and per umbrella entry, and gains `--check` for CI. It stays the source the handbook's API tab and the API review read.
- **The handbook** builds as today: `npm run handbook` runs `scripts/handbookData.mjs`, then `tsc -p handbook` and its own Vite config, into one HTML file. Its data script reads the new paths (the surface, the import-boundary rules from the packages' `package.json` files, the bundle check, Dyno's results). It isn't a package and never publishes; CI builds it in the `build` job so a broken figure fails there.

### What the build replaces

- 1.x's gulp tasks, its esbuild configuration, `Build/`, `index.cjs`, the zip, `build-ts` and `tsd-jsdoc`: removed with 1.x in CS-611. The root's `prepare` becomes `husky` alone. CS-612 removes what 2.0 itself has that the per-package build supersedes: `vite.lib.config.ts` (it becomes the umbrella's browser build), `tsconfig.lib.json` and `tsconfig.lib.widgets.json`.
- hitld's worktree setup (`.human-in-the-lead/policy.json`, an owner path) becomes `npm ci --ignore-scripts --no-audit --no-fund` and nothing else: no gulp, no 1.x builds. Its merge gates' `cd packages/next && …` become root commands in CS-835.
- A fresh clone builds and tests with `npm ci && npm run build && npm test` (CS-612's done-when). The data stores stay `npm run setup`.

## Parity and Dyno without 1.x's source

The owner's call: a pinned, published 1.x replaces every path into 1.x's tree.

### The dependency

```json
"devDependencies": {
  "cesium-1x": "npm:cesium@1.147.0"
}
```

- **An npm alias, at an exact version, in the workspace root.** The alias is needed because the umbrella will be named `cesium` in the same workspace. Its dependencies install beside it: `@cesium/engine` 26.x and `@cesium/widgets` 16.x hoist (2.0 publishes neither name), and `@cesium/core` 0.1.x nests under them, because the workspace's own `@cesium/core` is 2.x and doesn't satisfy `^0.1.1`. - **What the published packages carry (read 2026-11-21):** `cesium@1.147.0` has `Build/Cesium`, `Build/CesiumUnminified` and `Source/Cesium.d.ts`. `@cesium/engine@26.5.0` has its `Source/` modules, `Source/ThirdParty/basis_transcoder.*`, the sky box textures, `Source/Core/Ion.js` and `index.d.ts`, but not `Build/Unminified/index.js`. `@cesium/core@0.1.1` has its `Source/` modules (188 files). ### Dyno

- **`cesium1x.ts`'s `"repo"` build goes.** A 1.x configuration always names a released version, as `release.mjs` already supports, and the default is the dependency's version. Pages that need one 1.x (the parity harness) load the dependency, at `/cesium1x/`. Dyno's sweeps across versions keep the release store (`BENCH_CESIUM_DIR`, `~/.cesium-bench/cesium`), which `npm pack` fills and checks against npm's integrity hash. A parity test that only needs 1.x's math imports it as modules through the aliases, with no page global.
- **1.x at a git ref (`/cesium-ref/<sha>/`) goes.** Building 1.x at a commit needs 1.x's tree and toolchain, which the branch no longer has. An unreleased 1.x commit isn't a baseline; a released version is.

## Releases

Built in CS-613 (2026-11-22), with the owner's answers: Changesets plus one script (CS-888), npm trusted publishing from `release.yml` (CS-889), 1.x keeps `latest` until 2.0.0 (CS-890), and the paired 0.x numbering (CS-891).

### A changeset per change

Every change adds a changeset, a short file in `.changeset/`, in the same commit that closes its work item. It names the packages, the bump (major, minor or patch), and one or two sentences written for users: `npx changeset --minor @cesium/core -m "…"`, or `npx changeset` to be asked. A change with nothing for users (tests, docs, bench) adds an empty one, `npx changeset --empty`. CI fails a pull request that changes a published package without one ("CI"). The merge review checks the wording, and `npx hitld publish check --file .changeset/<name>.md` runs on it before the merge. The rule is in `AGENTS.md` and the `work-items` skill.

### The release record

A release record is the change `npm run release:version` writes (`scripts/release/version.mjs`), reviewed and merged through the merge queue like any change:

0. **The plan, with the tree untouched.** `changeset version` runs first in a scratch copy of the manifests, the lockfile and `.changeset/`. It stops, leaving the tree as it was, when the stable version it gives isn't new (a changeset naming only an experimental package would otherwise be swallowed by the paired number) or can't pair (a minor of 100 or more).
1. `changeset version` consumes the pending changesets: it sets the stable group's one version in every stable package and in each sibling dependency (exact), updates the root's reference to the umbrella, and writes each package's `CHANGELOG.md` section.
2. `scripts/release/lines.mjs`'s `applyPaired` writes the experimental line's paired version (below), then both lines are checked, the root's exact dev dependency on the umbrella included. Changesets 3.0.3 moves that dependency itself (a scratch copy, 2026-11-22, and `test/release.test.ts`); the check catches it if a later version doesn't.
3. `npm install --package-lock-only --ignore-scripts` moves the lockfile's workspace versions with them, so `npm ci` still agrees.

`npm run release:notes` prints the combined notes the GitHub release will carry, for the review.

**What counts as one** (`scripts/release/record.mjs`, the same check in CI's changeset rule and in `release.yml`): at least one changeset was pending at the base and every one is gone, none is added; under `packages/` only each package's `package.json` and `CHANGELOG.md` change, and no package is added or removed; under `.changeset/` only the consumed changesets and the pre mode's files change; each `package.json`, the root's included, changes only its version and its dependencies on siblings; every package's version goes up; and both version lines hold at the head. `test/release.test.ts` runs the real `release:version` in a small workspace and checks that its result passes, that putting back one changeset fails, and that the bypass the first version allowed (delete one changeset, change a package's `exports`) fails. Prereleases use Changesets' pre mode: `npx changeset pre enter alpha` once, in the change before alpha.1's record (it writes `.changeset/pre.json`), and `npx changeset pre exit` before 2.0.0. In a scratch copy of this layout on 2026-11-22, Changesets 3.0.3's first version in pre mode `alpha` from `2.0.0-poc.0` was `2.0.0-alpha.1` for all seven packages, and the consumed changesets moved to `.changeset/pre/`.

### Changelogs

- **Per package.** Each package keeps Changesets' default `CHANGELOG.md` (`@changesets/cli/changelog`), and each package's `files` lists it, so it ships in the tarball. A package has none until its first release record, so the packed check doesn't count it among the listed-but-missing files.
- **Combined release notes.** `scripts/release/notes.mjs` gathers every package's section for the release into one page, the umbrella first: a section per package with changes of its own, then one line naming the packages whose section only lists sibling updates, as a `fixed` group's members' sections do when the change was elsewhere. The GitHub release carries that page.
- **Nothing private reaches them.** A changeset passes `hitld publish check` before it merges, and the notes are made only from changesets.
- **The root `CHANGES.md`** is 1.x's history; the pipeline neither reads nor writes it.

### The versions

- **Lockstep.** `.changeset/config.json` has the stable packages as one `fixed` group, so every stable package releases at every version, changed or not, and the set an application installs always matches. A test (`test/release.test.ts`) checks that the group names only packages under `packages/`, that both lines are consistent, and that every private workspace outside `packages/` (Sandcastle, Dyno) is in Changesets' `ignore` list. `privatePackages.version` is on, so the packages version while they are still private.
- **The paired 0.x line** (CS-681, CS-891). Any package under `packages/` outside the fixed group is on the experimental line, and its version is derived from the stable one by `pairedVersion` in `scripts/release/lines.mjs`: `0.(100 × major + minor).patch`, with the same prerelease suffix. So `2.0.0-alpha.1` pairs with `0.200.0-alpha.1`, and `2.1.3` with `0.201.3`. OpenTelemetry pairs its majors the same way. Changesets versions such a package with a number of its own; `--apply` replaces it with the paired one, in its `package.json`, its sibling dependencies (exact) and its changelog's newest heading. `--check` (`npm run release:check`, in CI's `checks` job and before anything is staged) fails when the stable packages aren't at one version, when an experimental package isn't at the paired version, when a sibling dependency isn't exact (the root's dev dependency on the umbrella included), or when a stable package depends on an experimental one. A stable minor of 100 or more is refused, since it would pair with the next major's numbers. No package is on the experimental line today; which ones start there is set at beta.1.
- **Dist-tags.** Prereleases go to `next`, 2.0.0 and later to `latest` (`distTag`). 1.x's `cesium` and `@cesium/core` keep `latest` until 2.0.0 is final (CS-890, answer B); from 2.0.0 on, 1.x's own releases of those two names publish with `--tag 1x`, a change to 1.x's release task on `main` at that point. Before packing a `latest` release, the stage script checks with `npm view` that no package's `latest` would move to a lower version, comparing versions as semver does (a prerelease's numeric parts as numbers, so `alpha.10` is above `alpha.9`).

### The pipeline

`release.yml` runs on a push to the 2.0 branch that changes a `packages/*/package.json`.

1. **`record`** (Node only, no `npm ci`): `scripts/release/record.mjs --before <the push's before commit>`. A push can hold several commits (the owner pushes bundles from another machine), and its head's first-parent line needn't reach the before commit: a merge made by `git pull` puts the local line first and origin's old tip, the before commit, second, and a force push's before commit isn't an ancestor at all. So it judges every commit the push adds (`git rev-list before..head`, on every parent's side), each against its own first parent. A merge that only carries a version one of its other parents has (the merge of a branch that holds the record) counts as neither a record nor a stray, so a record is counted once. When the before commit is an ancestor of the head, a record or a stray at a version already tagged or on npm, or at or below the before commit's version and not built on it (its first parent doesn't descend from the before commit, `git merge-base --is-ancestor`), is a stale copy a merged side branch carries, and is skipped with a log line: a record written locally, with branches forked from it, that `pull --rebase` rewrote before its rewrite released. A commit built on the before commit is new work, never such a copy: after a record S that failed or was reverted, a push of S's revert and a new record at S's version holds a genuine record at the before commit's version, and it is staged. The head's own version is still checked, so skipping one can't hide a version. A force push keeps the full check, and its message says to leave a released record as it is rather than revert it. The push holds a release record when one commit is exactly one (above), the head is at that record's version, the version has no `v<version>` tag, and npm doesn't already have it (as after a record reverted and landed again; a draft GitHub release makes no tag). It outputs that commit's SHA, and every later job works on that commit, not on the push's head (`GITHUB_SHA`), and says so in its log. It never ends green while a version could be lost: it fails the run for two records in one push (naming both), for a commit that moves the umbrella's version up without being a record (one that landed after new changesets, say), for a record below the head's version, and, on every other path once the before commit resolves, for a head whose umbrella version is above the before commit's with no tag and not on npm. The next push's before commit is past such a version, so it would never release; each message gives the recovery (push each record by itself; rerun with "Re-run all jobs"; or revert, then write the record again from the tip). A record the head itself reverts (the head's version below the record's) isn't staged, and the run ends green, since no commit at the head carries that version. A force push's old tip is on no branch, so the job first fetches it by its id (a read); if it still can't be read, the job can't tell what the push added, and fails unless the head's version is already tagged or on npm. A push with no before commit (a new branch's first push) fails unless the head's version is already tagged or on npm: GitHub sends no before commit then, and judging only the commits on no other remote branch would miss a record pushed to another branch first. A malformed before commit holds none. Its output runs with workflow commands stopped, as the changeset check's does. Anything else ends here.
2. **`verify`,** with no OIDC token and no write token: `npm ci --ignore-scripts`, the version lines, `npm run build -- --no-checks` (the suite's bundle test reads `dist/`, so the build comes first), `npm test`, the bundle check and the surface check, on the record's commit (checked out by the SHA `record` gave). Then `node scripts/release/stage.mjs --pack`: it checks the version lines, refuses any package that is still `private` (npm won't stage one), checks that `latest` never moves down, runs the packed checks, and writes each checked tarball and `release.json` (the version, the dist-tag, and each tarball's SHA-256, siblings before their dependents and the umbrella last). It also writes the combined notes and the browser build's archive, with their `SHA256SUMS`. Both sets go up as artifacts, kept 30 days so they outlast a long wait for the owner's approval (the review put that wait at 30 days; GitHub's environments page states 30 days only for a wait timer), and the SHA-256 of `release.json` and of `SHA256SUMS` are the job's outputs.
3. **`publish`,** in the GitHub environment `npm`, whose required reviewer is the owner, the only job with `id-token: write`. It runs no `npm ci`, no build and no dependency's code: Node, npm, and `scripts/release/stageTarballs.mjs`, which imports nothing outside Node and its own folder. It refuses unless it runs in GitHub Actions with an OIDC token to ask for (so no local login ever stages), unless the `npm` environment itself, read through the REST API with the job's token (`gh api repos/$GITHUB_REPOSITORY/environments/npm` and `…/environments/npm/deployment-branch-policies`, both GETs), has a required-reviewers rule with a reviewer and custom deployment-branch policies (not "protected branches", which lets any protected branch deploy, `main` included) that are exactly one branch policy, `cesium-2.0-webgpu-poc`, and unless its `CESIUM_RELEASE_GATE` variable is `reviewed` (the checklist's first step). The environment's name is compared without case, as GitHub's names are. The API check is the real guard: `vars.` falls back to a repository's or an organization's variable of the same name, so the variable alone could be opened without the environment. The REST pages for both endpoints say "Anyone with read access to the repository can use this endpoint", but that describes users: GitHub's "Permissions required for fine-grained personal access tokens" lists both GETs under "Repository permissions for "Actions"", read, and its page for GitHub Apps gives them at read level too. So the job's `permissions` include `actions: read` beside `contents: read` and `id-token: write`. It couldn't be tried here, since nothing here runs a workflow; a failed read leaves no file, and the job fails closed. Last before staging, it refuses when an earlier run staged this version or is staging it: `verify` names its tarballs' artifact `npm-tarballs-<version>`, and `publish` (`scripts/release/earlierRuns.mjs`) lists only this workflow file's runs on the 2.0 branch from pushes (`GET …/actions/workflows/release.yml/runs?branch=cesium-2.0-webgpu-poc&event=push`) whose head repository is this one, then each other run's artifacts of that name (`GET …/actions/runs/<id>/artifacts?name=`, the version URL-encoded) and, for a run that has one, its jobs, every attempt's (`GET …/actions/runs/<id>/jobs?filter=all`). It refuses when one of those runs' `publish` job succeeded or hasn't finished, or the run is still going with no `publish` job listed yet (a record removed by a force push and pushed again makes two runs for one version). The repository-wide artifact list it once read covers every workflow, so a fork's pull request could add one that uploads `npm-tarballs-<next version>` and make every genuine publish refuse; this way no other workflow and no fork counts. It lists only runs created in the last 35 days (`created=>=<date>`): `verify`'s artifacts last 30 days and the review put the approval's wait at 30, so an older run can't still stage, and the GETs (one artifacts list per run, against the job token's limit, which the review put at 1,000 requests an hour) stay bounded however long the history grows. Every list is read page by page until a page is short, never stopping on `total_count`, which can be stale or capped; a list that reaches 1,000 results fails the step, since GitHub's "List workflow runs for a workflow" page says "This endpoint will return up to 1,000 results for each search" with `branch`, `event` or `created`, and a page it can't read fails it too, so nothing is staged. npm's own `npm stage list` can't help here: npm's stage page says the short-lived tokens trusted publishing issues "cannot run `npm stage` subcommands". A draft release can't either: GitHub's releases page says "Only users with push access will receive listings for draft releases", and "Get a release by tag name" gets "a published release"; the job's token has `contents: read`, not write. Artifacts last 30 days; past that, npm itself refuses the second staging at the first package, before anything new is staged, since its stage page says "Staged packages share the same semver version unique index as published packages"; the job's message then says to approve or reject the earlier staging. Then it checks `release.json` against the sum `verify` reported and each tarball against `release.json` (its sum, its name and version, not private), then stages each in order: `npm stage publish ./<tarball> --tag <tag> --access public --ignore-scripts`, through npm's trusted publishing (the job's OIDC identity, no npm token anywhere, provenance attached by npm). It checks that the runner's npm is 11.15.0 or later, the first with `npm stage publish`; Node 24's current npm is 11.19.1. npm 11.17.0's source, read 2026-11-22, settles the flags: `lib/commands/stage/publish.js` is `class StagePublish extends Publish` with `static params = Publish.params`, so it takes `npm publish`'s spec and flags (`tag`, `access`, `dry-run`, `provenance`); `lib/commands/publish.js` resolves the spec with `npa` ("you can publish name@version, ./foo.tgz, etc"), and runs `prepublishOnly`, `publish` and `postpublish` only for a directory, as libnpmpack does `prepack` and `postpack`, so a tarball runs no script and `--ignore-scripts` (a global setting the command reads) only says so. Its `--dry-run` skips only the upload: it still asks for the OIDC token in CI and reads the name's versions from the registry, so a dry run in a job with `id-token: write` would exchange a token. `publish` never dry-runs, and a local dry run (`stage.mjs --dry-run`) sends no token, since npm asks for one only in CI.
4. **A maintainer approves** each staged version on npm with 2FA, the umbrella last. Nothing is live until then. A staging failure partway leaves the packages before it staged; the job's message names them, and the owner rejects each (`npm stage list`, then `npm stage reject <id>`, with 2FA) and reruns the workflow. npm refuses to stage a version that is already staged ("Staged packages share the same semver version unique index as published packages", npm 11.17.0's `npm help stage`); npm's command line itself checks only the published versions before it uploads (`lib/commands/publish.js`), so the refusal is the registry's.
5. **`github-release`,** the only job with `contents: write`, which runs nothing from the repository: it checks the notes and the archive against the sum `verify` reported, then creates a draft GitHub release tagged `v<version>` at the record's commit (the SHA `record` gave). The owner publishes it after the npm approvals.

**Concurrency.** GitHub cancels a pending run in a concurrency group when a newer one queues, so the workflow has no group of its own: a later push could otherwise cancel a record's run while it waits for the owner. Each job after `record` takes a group keyed by the record's commit, which only a rerun of that record shares. A record's run that fails or is cancelled for another reason is recovered with GitHub's "Re-run all jobs", which keeps the run's event, so its before commit and its record.

**Why the split.** Every step of a job with `id-token: write` can ask for an npm credential, vite, rollup, tsc and every build plugin from the dev dependencies included. Building in `verify` and staging the checked tarballs in a job that runs none of them keeps that credential away from dependency code, and a trusted publisher limited to `npm stage publish` keeps even a stolen one behind the owner's 2FA approval. The split protects the credential, not the content: the tarballs are built in `verify`, with the dev dependencies' code running, and the checks after it (the sums, the names and versions) prove only that `publish` stages what `verify` made. So the maintainer's 2FA approval on npm is the only check on what the tarballs hold.

**Why this, and what it replaces.** 1.x releases by hand: `gulp release`, `make-zip`, `deploy-set-version`, a maintainer's machine and token. Current practice publishes from CI with short-lived OIDC credentials (npm's trusted publishing, generally available since July 2025), and npm's staged publishing (2026) adds a human approval with 2FA in front of what CI uploads. That approval matters: Socket reports that in May 2026 a project's trusted publisher itself published malicious versions, with no token stolen. Staging plus the owner's environment approval puts the owner in front of every release, which is also how this repository's merges already work.

**The tools it doesn't use.** `changeset publish` and the Changesets GitHub action: the action's version pull request would bypass the merge queue, and `changeset publish` publishes directly rather than staging, so `release.yml` stages with npm itself. A repository script driven by `releases/<version>.md`, this design's first recommendation, which CS-888 set aside for Changesets. release-please reads Conventional Commits, which this repository's commits aren't, and reports of its `linked-versions` plugin failing to find release candidates make it a poor fit for lockstep (sources below).

**Bootstrapping the names.** npm's trusted publisher is configured on a package's settings, and npm's `npm trust` page says the package must already exist. Staged publishing can create a package that doesn't exist (npm publishes a `0.0.0-stage` placeholder, which is public), but a trusted publisher can't be configured for it beforehand. So names that have never been published (most of the package map's list) need a first publish by a maintainer, by hand, before the workflow can publish them. `cesium` and `@cesium/core` exist, and 1.x publishes them; npm allows several trusted-publisher configurations per package (up to 10, its trusted-publishers page says; its `npm trust` page says one, so the owner checks which holds when setting it up). Which names, and when, is CS-616's.
